# Contributing

Thank you for helping out! This app is a hobby project used by several hundred Viessmann owners, so the most important thing is that an update never breaks what already works for them. The ground rules below exist because each of them has cost something before.

How the app is built is described in [docs/ARCHITECTURE.md](docs/ARCHITECTURE.md). Setup and commands are in the [README](README.md#development).

## Ground rules

1. **No breaking changes for existing users.** These are frozen once released: capability IDs, Flow card IDs, Flow card argument names, types and dropdown values, trigger tokens, the device `data.id`, store keys and the device class. Renaming or removing a capability deletes the user's Insights history and breaks their Flows; it happened once, in v1.0.11. The registry test (`drivers/vicare/__tests__/registry.json`) fails if anything released disappears. Adding is fine; retiring something is the maintainer's decision and gets a `retired` entry with the reason. Never reuse a retired ID.
2. **Capabilities are only ever added automatically, never removed.** When the stored feature list is refreshed, merge the old and the new list; never replace it. A sensor that happens to report `notConnected` at the moment of an upgrade must not lose its capability.
3. **Never commit real API dumps.** Feature and installation dumps contain serial numbers, installation IDs and sometimes addresses. Keep them in the local, ignored `documentation/` folder and turn them into test fixtures with `scripts/anonymizeDump.js`, which uses the same rules as the app's troubleshooting data (`lib/anonymize.js`; see [test/fixtures/README.md](test/fixtures/README.md)). `test/fixtures.privacy.test.js` must pass.
4. **English everywhere in the repository:** code, comments, test names, documentation, commit messages and pull requests. User-facing texts are localized (English, German, Dutch, French, Swedish).
5. **Don't edit generated files by hand.** `app.json` is generated by the Homey CLI from `.homeycompose/` and the driver compose files; the capability matrix (`drivers/vicare/__tests__/capabilityMatrix.json`) by `npm run matrix`. The Flow cards in `drivers/vicare/driver.flow.compose.json` are edited by hand, with their texts inline in every language they have, and each card has a `$filter` on the capability it works on.
6. **Use the live Viessmann datapoint list and avoid deprecated datapoints.** Viessmann marks datapoints `deprecated` with a removal date: <https://api.viessmann-climatesolutions.com/documentation/data-points>. Read command limits (`params.*.constraints`, `isExecutable`) from the API at runtime instead of hard-coding them. Check what a datapoint means before mapping it: some values that look like measurements are settings.
7. **Handle every promise.** Await or `.catch()` every SDK call such as `setAvailable`, `setUnavailable` and `setCapabilityValue`. Unhandled rejections are reported as crashes and can stop the app.
8. **Keep the API quota in mind.** Viessmann's free plan allows about 1,450 calls per day per user, and the app polls every two minutes per device. New features must not add calls per poll.
9. **No misleading values.** Users should be able to trust what they see, so use judgement. Rounding, the resolution of the poll interval, Homey's own energy (kWh) calculation and Viessmann's own figures are fine. Values that are wrong in substance are not: meters the app builds itself that drift, guesses or estimates the app makes up, stale values shown as current, and values derived from something that is missing. Leave such a value empty instead. Users who want their own sums can build them on the app's values, for example with the Power by the Hour app.

## Reporting a bug

- What you expected and what happened, with your Homey version, app version and Viessmann model.
- If you can, send a diagnostic report from Homey (the app's page > *Send diagnostic report*) with a short message, and mention it in the issue.
- The report for the developer from the app settings (*Troubleshooting* > *Prepare report*) helps a lot. The app anonymizes it automatically (serial numbers, IDs and the address become placeholders such as `anonymized-serial-1`), but please still send it privately, for example as a private message on the Homey Community forum, rather than paste it into a public issue.

## Pull requests

- For anything larger than a small fix, open an issue first so we can agree on the approach.
- One topic per pull request. Behavioural changes need tests; the anonymized fixtures in `test/fixtures/` make that possible without a real installation.
- Before pushing: `npm ci --ignore-scripts`, `npm run test:coverage`, `npm run lint`, `npm run typecheck` and `npm run homey:validate`. CI runs the same checks, plus a check of the app package and CodeQL.
- When a change alters what a device gets (capabilities, their options, Flow cards), run `npm run matrix` and commit the updated capability matrix: its diff shows the effect per installation type.
- New code follows [Code structure](#code-structure) below.
- Please allow edits by maintainers. Small fixes may then be added to your branch as separate commits on top of yours, so your commits stay yours. If your work is used in another way, you are credited with a `Co-authored-by` trailer and in the changelog.
- Releases go to the Homey test channel first, so expect some time between merge and the App Store.

## Code structure

Guidance rather than rules: use judgement, and leave the code easier to follow than you found it. [docs/ARCHITECTURE.md](docs/ARCHITECTURE.md) shows where things live.

- **One module, one job.** The comment at the top of a module says what it does, in a sentence or two. `device.js` and `driver.js` hold the device's and the driver's state and wire the Homey SDK to the modules; the logic is in the modules.
- **Logic as pure, testable functions, with Homey SDK calls at the edges.** Decide in a function that takes plain values and returns one (which capabilities a device gets, what to store, which message to show), and keep `setCapabilityValue`, `setStoreValue`, API calls and timers in the thin function that applies the decision.
- **Split a file or function when it gets hard to follow, not at a line count.** Code that mixes several jobs, or that you have to read up and down to understand, is worth splitting; a long but plain table of configuration is not.
- **Reuse before writing new.** Look for the module that already does the job and extend it: every command goes through `commands.js`, every error shown to users through `userErrors.js`, every Flow card through `flowCards.js` and `flowHandlers.js`.
- **New datapoints are configuration, not code.** A new Viessmann value is an entry in `drivers/vicare/config/` (see *Add a datapoint* in the architecture document); change code only for what the configuration cannot express.
- **Types and tests next to the code.** A new module starts with `// @ts-check`, its exported functions have JSDoc types, and its tests are in the `__tests__/` folder next to it.
