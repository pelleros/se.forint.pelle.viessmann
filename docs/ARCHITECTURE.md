# Architecture

How the Viessmann ViCare app for Homey is built. For the ground rules see [CONTRIBUTING.md](../CONTRIBUTING.md); for commands see the [README](../README.md#development).

## What the app is

A Homey Pro app that integrates Viessmann heating systems (heat pumps, gas boilers, fuel cells) through the [Viessmann IoT API](https://api.viessmann-climatesolutions.com/documentation). Each paired ViCare device represents one Viessmann device and polls its features from `api.viessmann-climatesolutions.com/iot/v2`; optional extra devices show one part of a Viessmann device on their own (see [Extra devices](#extra-devices)).

- **App ID:** `se.forint.pelle.viessmann`, Homey Apps SDK v3, `platforms: ["local"]`. Drivers: `vicare` (the ViCare device), and the extra devices' `heating-circuit`, `hot-water` and `room`.
- **Runtime:** Node.js 22 (`compatibility: >=13.5.0`; Homey runs apps on Node 22 from Homey 12.9).
- **Auth:** OAuth2 with PKCE (a new code verifier per login) via `homey-oauth2app`. Every user registers their own Client ID on the Viessmann developer portal and enters it in the app settings.

The design choice that shapes everything: **there is one device type for every Viessmann product.** A device gets its capabilities at runtime from the features its installation reports, instead of having a fixed capability list per product. The extra devices follow the same rule within their part (a heating circuit, the hot water, a room).

## Device and driver

`device.js` and `driver.js` hold the state the Homey SDK gives them (the device's ids, stored metadata, roles and settings being saved; the driver's pollers and trigger cards) and wire the SDK's lifecycle to the modules; the logic is in the modules (see *Code structure* in [CONTRIBUTING.md](../CONTRIBUTING.md)):

| When | Device method | Module |
|---|---|---|
| Start | `onOAuth2Init` | `migrations.js`, then `capabilitySetup.js` (capabilities, options, modes, listeners), `boost.js`, polling |
| Poll response | `onFeaturesUpdated`, `setCapabilityValueIfPossible` | `featureUpdates.js`, with `deviceMetadata.js` (new features, learned roles) and `deviceMonitor.js` |
| Write | `writeCapability`, `executeCommand`, `showWrittenValues`, `checkOperatingMode` | `capabilityWrites.js`, which sends through `commands.js` |
| Setting changed | `onSettings`, `applyEnabledGroups` | `deviceSettings.js` |
| Metadata refresh, circuit change, maintenance action | `refreshStoredMetadata`, `mergeRefreshedMetadata`, `applyCircuitMetadata` | `deviceMetadata.js` |

The module functions take the device as their first argument and call its methods for the steps another module or a test may replace (`device.initializeCapabilities()`, not the module's own function), so a method stays on the device as a one-line delegation that returns the module's promise. Decisions that need no device are exported as pure functions and tested on their own (`optionsPath`, `mergeMetadata`, `readDeviceMetadata`, `circuitSetting`, `pollFilter`, `pairedDevice`, `retryDelay`, `pollErrorMessage`, …). The driver keeps its pollers (`_startPolling`, `_pausePolling`, `_resumePolling`, `_stopPolling`, and `follow`/`unfollow` for the extra devices), the trigger cards per capability and `onPairListDevices`, and takes the rest from `pollPlan.js`, `lib/apiError.js`, `lib/errorMessages.js`, `pairSession.js`, `deviceMetadata.js` and `flowHandlers.js`.

## Commands and packaging

`npm install`/`npm ci` only install dependencies (use `--ignore-scripts`). Anything that talks to a Homey goes through `npm run homey:run`, `homey:install`, `homey:validate` or `homey:publish`. The Homey CLI packages the app folder minus the patterns in `.homeyignore` (`documentation/`, `test/`, `docs/`, `scripts/`, `__mocks__/`, `__tests__/`, `*.md`, `package-lock.json`, …) and its own defaults (dotfiles, `node_modules`, `*.compose.json`, `*.ts`, `tsconfig.json`, `env.json`), then adds the production dependencies. CI runs `homey app build` and `scripts/checkPackage.js`, which prints the package size and fails if tests, fixtures or API dumps, documentation, scripts, Markdown files, the lockfile or the dev twin's fixture mode (`fixtureMode/`, `app.store.js`, or any file with its marker) end up in the package; when you add such files somewhere new, add them to `.homeyignore`.

The type check (`npm run typecheck`, `tsconfig.check.json`) runs `tsc --noEmit` on every file with `// @ts-check`, with the Homey SDK types (`@types/homey`) and `types/homey-oauth2app.d.ts`. It uses the TypeScript that `eslint-config-athom` installs: `typescript` must not become a devDependency, because the Homey CLI would then build the app as a TypeScript app. The root `tsconfig.json` stays as it is: ESLint's TypeScript rules use it for every file. ESLint stays on version 8, the only one `eslint-config-athom` supports.

## `drivers/vicare/config/`

The place to change when adding or removing a Viessmann datapoint. `require('./config')` (the `index.js`) combines one module per theme, so that changes to different themes touch different files:

| Module | Theme |
|---|---|
| `thermostat.js` | Set points and modes: hot water and heating targets, operating mode, one-time hot water charge, fuel cell mode, and Homey's standard thermostat (`target_temperature`, `measure_temperature`, `thermostat_mode` without a suffix) |
| `temperatures.js` | Temperature sensors outside the heating circuit (hot water cylinder and its middle, bottom and top sensors, outside, buffer, return, primary/secondary circuit, boiler, fuel cell, compressor) |
| `circuits.js` | Readings of the heating circuit (room, circuit temperature, supply, frost protection, heating curve) |
| `status.js` | Running states (compressor, burner, heating rod), compressor load, burner modulation, fuel cell phase; faults, logbook, the problem alarm and the maintenance action |
| `energy.js` | Power, the heat output now, Viessmann's consumption for yesterday, coefficients of performance, the seasonal efficiency figures (SCOP and SPF, own capabilities, never shown as a COP; a 0 for a part that has not run yet shows as no value), the statistics counters (also the heating rod's) and the daily figures of the compressor and burner counters |
| `pumps.js` | Circulation pumps (on/off), and the factory for on/off states |
| `hotWater.js` | Hot water charging |
| `solar.js` | Solar thermal collectors (collector and hot water temperature, solar pump) |
| `program.js` | Heating programs: the program picker, the reduced and comfort set points, the holiday program; hot water mode and hysteresis |
| `state.js` | What the device is doing now: heating now, the operating state, the status text |
| `modes.js` | Titles of the operating modes and their mapping to Homey's standard thermostat mode (no `PATHS`; used by `thermostat.js` and `capabilitySetup.js`) |
| `templates.js` | Shared option templates and the factories below |
| `order.js` | The order of `PATHS` and the capability order of new devices |
| `types.js` | JSDoc types of the configuration |

Every theme module exports `PATHS` and `FEATURES` for its paths, and optionally `DERIVED`; a new theme module is added to `MODULES` in `index.js`. The index exports:

- `PATHS`: feature path constants, e.g. `HOT_WATER_TEMP: 'heating.dhw.sensors.temperature.dhwCylinder'`. The filtered poll requests exactly `Object.values(PATHS)`, so a feature without a `PATHS` constant is never polled. `order.js` → `PATHS` keeps the path order of 1.0.16 (also the order of the poll filter), and paths it does not list follow in module order. `index.js` refuses a constant or path defined twice.
- `CAPABILITY_ORDER` (`order.js` → `CAPABILITIES`): the order in which a newly paired device gets its capabilities, and so the order on its tile, in groups: 1 the heating thermostat, 2 operating mode and program, 3 hot water, 4 status, 5 temperatures, 6 energy and efficiency, 7 statistics, then everything else. An entry is a capability ID or a prefix ending in `*`; a capability takes the place of its exact entry, else of the first matching prefix, and capabilities with the same place keep the `PATHS` order. Existing devices keep their order: Homey shows capabilities in the order they were added, and new ones are appended (removing and re-adding would delete history and break Flows).
- `DERIVED`: capabilities computed from one or more features, possibly of other theme modules (the standard thermostat's room temperature and mode, the program picker, heating now, the operating state, the status text). Each has `sources` (feature paths it reads; it is added when one of them is stored and allowed by that path's `requireRole`, and `available(features)` can add a condition), `derive(read, context)` (the value from a response: undefined keeps the last value, null means unknown; `read(path, propertyPath)` gives only enabled, connected features the roles allow, and `context` has the readings before it and Homey's language), `capabilityOptions`, `options(context)` for options that depend on the device (enum `values` from its operating modes or stored features) and `write(value, context)` when it is writable (the commands to send, in order, and the values to show afterwards; it throws an error whose `code` is a `flow.*` key for a value the device cannot take, which `userErrorFrom` turns into the user's text). `index.js` refuses a derived capability with the name of another capability.
- `FEATURES`: `{ [PATHS.X]: { requireRole?, fallbackFor?, capabilities: [...] } }` in the same order, mapping a feature path to one or more Homey capabilities.
- Helper factories (in `templates.js`): `createTemperatureCapability`, `createThermostatCapability`, `createActiveCapability`, `createModulationCapability`, `createCopCapability`, `createStatisticsCapabilities`, `createFuelCellStatisticsCapabilities`.
- Lookups used by `capabilitySetup.js`, `device.js` and `flowCards.js`: `getCapability(path)`, `getAllCapabilities(path)`, `getCapabilityOptions(capabilityName)`.

Each capability entry has:

- `capabilityName`: usually a sub-capability, e.g. `measure_temperature.hotWater`. The part before the dot is a Homey system capability or a custom base in `.homeycompose/capabilities/`. A feature path can feed several capabilities (the normal program feeds `target_temperature.heating` and the standard `target_temperature`).
- `propertyPath`: dot path inside the feature's `properties`, e.g. `value.value`, `active.value`, `hours.value`.
- `command` *(optional)*: how to write back via `executeCommand`, either `{ name, parameterMapping }` or `{ useValueAsCommand: true }` with a `valueMapping`.
- `valueMapping` *(optional)*: maps API values to capability values.
- `enumParameter` *(optional)*: for an enum capability, the command parameter whose `enum` constraint lists the values the device accepts; its `values` are narrowed to them (unknown ones get a title made from their id).
- `computed` *(optional)*: the device computes the value itself instead of copying `propertyPath` (which then names the property it is computed from); see *Computed values*. `readValues` leaves such capabilities out.
- `capabilityOptions`: passed to `setCapabilityOptions` (title, units, min/max/step, decimals, `preventInsights`, `preventTag`, enum `values`).
- On the feature: `group` (e.g. `diagnostic`) puts its capabilities in an optional group (see *Optional groups* below). `requireRole` (`type:heatpump`, `type:boiler`, …) limits the capabilities to devices whose roles contain it. `roles.js` widens this: a `type:*heatpump*` role (e.g. `type:dhwHeatpump` on a hot water heat pump) counts as `type:heatpump`, and a device whose roles contain neither tag (newer models) gets `type:heatpump` inferred from `heating.compressors.N` (or an enabled compressor in `heating.compressors`) and `type:boiler` from `heating.burners.N` (or `heating.burners`). Both only add capabilities: a device without role tags keeps every capability whose feature is stored. `fallbackFor` (another feature path) makes the entry a second source for the same capabilities: it is read only when the other path gives no value. The capability is added when either path is in the stored feature list, and both paths are polled. `alwaysAdd` gives every device the feature's capabilities, also when it does not report the feature (`alarm_problem` and the maintenance action `button.refreshFeatures`, both on `device.messages.errors.raw`, which feeds the alarm where a device has it).

## `drivers/vicare/featureMapper.js`

The mapping between feature responses and capabilities, as pure functions without any Homey dependency, so that tests and tools can use it directly. The device and driver modules use the shared instance `featureMapper`:

- `capabilitiesFor(storedFeatures, roles, enabledGroups)`: the capabilities a device gets (derived ones included), in the capability order of new devices (`derivedCapabilities.js` holds the order and derived-capability helpers), with the features of optional groups that are off left out (`isInEnabledGroup`); `isProduced(name, storedFeatures, allowPath)`: whether a stored feature still produces a capability.
- `optionsFor(name, path, constraints, context)`: the configured options with the API's temperature limits (`temperature` or `targetTemperature` of the path's command, else the limits of the capability's own command parameter from `context.commandMetadata`) as min/max/step, enum values narrowed by `enumParameter`, and a derived capability's device-dependent options.
- `readValues(response, roles, context)`: every capability's value from a circuit-normalized response (main paths before `fallbackFor` paths, derived capabilities last; see *Updating values* below); `displayValue(name, value)` applies `valueMapping`.
- `updatedCommands`, `newFeatures`, `deviceMetadata` (what pairing stores: features, constraints, command metadata, operating modes), `commandTarget(name, storedFeatures)` (the path and capability a write goes through: the first path producing the capability that the device has stored, so a device whose programs have newer names writes to its own), `writableCapabilities()`, `derivedByName(name)` and `mergeOperatingModes(current, deviceModes)`.

## Dynamic capabilities

`driver.compose.json` declares no capabilities; each device is shaped at runtime (`capabilitySetup.js`).

1. **Pairing** (`driver.js` → `onPairListDevices`): lists installations, gateways and devices of type `heating` (`pairSession.js` → `heatingDevices`), fetches each device's features once (`_getEnabledFeaturesAndOpModes`, read by `deviceMetadata.js` → `readDeviceMetadata`) and stores per device (`pairedDevice`): `heatingCircuitId` (see below), `features` (enabled, not `notConnected`), `constraints` (min/max/step/enum per command parameter), `commandMetadata` (the API's `commands` per feature), `operatingModes` (from `setMode` on the circuit's `operating.modes.active`), `roles` and `version`.
2. **Init** (`device.js` → `onOAuth2Init`, the steps in `capabilitySetup.js`): `checkUpgradeSpecifics()` runs the store migrations the device needs (see *Versions and migrations*), including a one-time metadata refresh for pairings without `heatingCircuitId`/`commandMetadata` (the stored feature list becomes the union of the old and the fresh list; a failure is logged and retried on the next start); `initializeCapabilities()` adds the capabilities of every stored feature that passes the role check and whose optional group (if any) is on (`featureMapper.capabilitiesFor`, with API constraints merged into `min`/`max`/`step`) and, today, removes capabilities that no longer map to a stored feature (or whose group is off); `updateCapabilityOptions()` reapplies the options from the config and the constraints on every start; `initializeOperatingModes()` sets the `values` of `thermostat_mode.heating` to the device's modes; `registerCapabilityListeners()` registers one listener per writable capability (with a command or a derived `write`; a value that equals the current one sends nothing, so a Matter bridge or voice assistant repeating the set point costs no API call); pending temporary changes from Flows are scheduled again (see *Temporary changes* below).
3. **Polling** (`driver.js` → `_startPolling`, `lib/DevicePoller.js`; the plan in `pollPlan.js`): one poller per Viessmann device, shared with the extra devices that show part of it (see [Extra devices](#extra-devices)), every `2 minutes × number of polled devices` (the device setting `pollInterval` "auto"), or the device's own interval in minutes (`pollInterval`: 2–60), counted from the end of the previous poll, so polls never overlap. Every API request times out after 30 seconds, for the response and its body (`onBuildRequest` in the OAuth client, `lib/http.js`), and a poll that has not finished after 100 seconds counts as failed: its result is ignored and the next poll is scheduled. Stopping a poller waits at most 5 seconds for a poll in progress. Failures back off (doubling, at most 30 minutes) and honour `Retry-After`. When only a new login helps (the API still answers 401 after a token refresh, or the token endpoint answers 401, `invalid_grant` or `invalid_client`), the device becomes unavailable right away with "Authentication failed, open the device and choose Repair". Other token refresh failures (network, timeouts, 5xx) are temporary like any other error. Some errors make the device unavailable right away with a translated message (`locales/*.json` → `errors`; `pollErrorMessage` in `lib/errorMessages.js` decides what a device says) and set the least wait before the next poll (`retryDelay` in `lib/apiError.js`): HTTP 402 / `PACKAGE_NOT_PAID_FOR` (Viessmann refuses access to the account's data, often a temporary fault on its side; next poll after 1 hour), HTTP 429 when the reset time is known from `Retry-After` or the body ("updates resume at HH:MM" in Homey's time zone; the poll waits until then) and `GATEWAY_OFFLINE` (at least 5 minutes, then the usual backoff). Other errors: three failures in a row make the device unavailable with the API error (or "Multiple communication errors"). The next successful poll makes it available again, and every successful update calls `setLastSeenAt()` (a failure there is only logged). A response entry that is no feature object, or a value that is no string, boolean, finite number or null, is skipped; the rest of the response is applied. About 3 % of polls request all features instead of only `PATHS` (`isExtendedPoll`; the filter is `pollFilter`); new enabled features are then added to the stored list (it only grows) and get capabilities and listeners. Deleting a device stops its poller (extra devices that share it keep it) and drops a poll still in progress.
4. **Updating values** (`onFeaturesUpdated`, `featureUpdates.js`): refreshes the command metadata from the response, then reads every capability's `propertyPath` (`featureMapper.readValues`), primary feature paths before `fallbackFor` paths and the derived capabilities last, and calls `setCapabilityValueIfPossible`, which compares the value as the capability shows it (after `valueMapping`) and, when it changed, sets it and fires the matching trigger cards (see *Flow cards*). The response's features are also remembered for the generic read cards. When none of a capability's paths is reported as an enabled, connected feature (`notConnected`, disabled or missing from the response), its value becomes `null` without firing a trigger; the capability stays. A response without any mapped feature clears nothing. Then `deviceMonitor.js` handles the response (computed values, status, write checks); a failure there is logged and never makes the device unavailable.

## Computed values

`computedValues.js` (pure, no Homey dependency) computes the capabilities marked `computed`, from the same poll response (no extra API calls), with `dailyCounters.js` for the counter figures. Each value has a sound basis or is `null`:

- `power` (`measure_power`, so the device appears in Homey Energy): the device's own consumption, or the inverter output as `fallbackFor`; kW and W are converted to W, any other unit gives no value. The heat output now (`measure_heat_output`) is converted the same way; it has its own capability because Homey Energy would count `measure_power` as electricity the device uses.
- `consumptionYesterday` (`measure_electricity_yesterday.*`, `measure_gas_yesterday.*`): `day[1]` of the feature's day values, but only when `dayValueReadAt` is today in Homey's time zone (then `day[0]` is today and `day[1]` the complete day before); older values are stale and give `null`. The unit comes from the response (electricity only in kWh; gas in m³ or kWh, set as the capability's `units` on the device).
- `startsToday`, `startsYesterday`, `runtimePerStartYesterday` (`measure_{compressor,burner}_number.*`): differences of the starts and hours counters from a midnight baseline (Homey's time zone), kept per counter in the store key `dailyCounters`. A new day takes the last reading before midnight as its baseline when that reading is at most the device's poll interval plus 10 minutes (and at least 35 minutes; 35 minutes when the interval is not known) before the first one after midnight; `deviceMonitor.js` passes the interval from `driver._calculatePollInterval`. Otherwise (offline, restarted or in a long backoff around midnight) the day has no baseline. A counter that goes backwards drops today's baseline. The average run time per start needs at least ten times the hours counter's resolution (0.1 h, or 1 h for counters that never showed tenths).
- `startsLastHour`: the difference with the newest reading at least an hour old and at most 95 minutes old, kept in memory (empty for an hour after a start). This does not follow the poll interval: with hourly polling the reading one poll back is taken, and with polls more than about 95 minutes apart the figure stays empty rather than cover far more than an hour.

## Device status

Pure modules read each response and `deviceMonitor.js` applies the result (texts in `statusMessages.js`):

- **Faults** (`faultLog.js`): the entries of `device.messages.errors.raw` and `fuelCell.errors.raw`. A code that is new fires the trigger `fault-reported` and a timeline notification once; the codes already reported are kept in the store key `knownMessages`, so a restart does not report them again.
- **Logbook** (`faultLog.js`): entries of `device.messages.logbook` newer than the newest one seen fire `logbook-entry-added` (the first logbook seen is history).
- **Frozen values** (`frozenValues.js`): when the newest feature `timestamp` of the responses has not moved for 6 hours of successful polls (only what the app has seen counts, not the age of the timestamps).
- **Writes** (`writeChecks.js`; `commands.js` remembers each successful write with the values to confirm: a capability's value, both heating curve values): after a successful command, the polls at least a minute later check that the capability reports the value written (set points and modes; not the one-time charge). One poll with the value confirms it. Since Viessmann's data can lag, only two polls in a row with another value count as not taken; a poll without the value starts the count again, and while the values count as frozen nothing is judged. A write whose value no poll reports within 15 minutes (frozen polls count as not reporting it) is forgotten silently. A write that did not take gives the user one notification and a warning, which goes when the value shows up or after 6 hours.

`alarm_problem` is on while there is a fault or frozen values; the device's warning (`setWarning`) says what is wrong, including a write that did not take. An enabled feature that suddenly reports no commands keeps the ones it had (`updatedCommands`), and a refused command (HTTP 403) says it may be temporary; nothing is removed for either.

**Event log** (`eventLog.js`; device setting `eventLog`, off by default; every 15, 30 or 60 minutes): `getEventsHistory` reads the installation's event log for the gateway since the last read (position in `knownMessages.events`), keeps the events of this device and fires `event-logged` and `event-code-logged` (whose run listener compares the card's `code` argument). Logbook and event log keep how far they have been read in the same way (`messageEntries.js`: the newest time seen and the entries at that time). Events older than two intervals (e.g. from while the app was off) are not triggered.

**Maintenance action** `button.refreshFeatures` (*Device settings > Maintenance*): reads all features once, merges them into the stored metadata (the list only grows), adds the capabilities of new features and shows the values; at most once per 10 minutes.

## API quota

`lib/apiQuota.js` counts every API request (`_executeRequest` in the OAuth client) per OAuth session (Viessmann login; `app.js` gives each client its session id) and UTC day, in the app setting `apiCallsToday`, written at most once a minute. `pollPlan.js` gives a device's interval and adds up the polls and event log reads of a session's devices (`driver.plannedCallsPerDay(sessionId)` collects their settings, and adds the polls made only for extra devices: a Viessmann device without a ViCare device, and the rooms' 15-minute polls); a device setting that would plan more than 1,400 calls a day (Viessmann allows about 1,450, and some are kept for pairing, the maintenance action and troubleshooting) is refused with a translated message before anything changes (`deviceSettings.js`). The dropdown labels show the calls a day of each choice.

Every write also needs the account's allowance (`writeQuota.js`, run by `sendFeatureCommand` after the command's own checks): it is refused only when the calls left today would no longer cover the account's planned updates until 00:00 UTC (pro rata), or when the account has sent 20 writes in the last 10 minutes (`WRITE_BURST_LIMIT` in `lib/apiQuota.js`, which keeps a window per session in memory; Viessmann's own limit is 120 calls per 10 minutes). The user sees `flow.write_quota_reserved` or `flow.write_burst`. Undoing a temporary change (`restoring`) is never refused.

## Pairing

`pairSession.js`, wired in `driver.onPair`; `driver.compose.json` → `pair`: `client_id` (custom view: asks for the Client ID when none is saved, with the redirect URI and a copy button; `save_client_id` checks it for spaces and length), `login_oauth2`, `pair_check` (custom view), `list_devices`, `add_devices`. `onPair` wraps the SDK's `list_devices` handler: `pair_check` runs it once, and the device list reuses the result for 5 minutes (one API read). `onPairListDevices` throws a translated message when the account has no installation or no device of type `heating` (listing the types it has). New devices are named after the model id (`E3_Vitodens_200_0821` → "Viessmann Vitodens 200"), or after their role when the id is no product name, with a number for a second device of the same name. The OAuth client reads the Client ID again when a login starts, so a Client ID saved in `client_id` is used right away. In fixture mode the dev twin points the views at `login_credentials`.

## Report for the developer

`lib/report.js` collects, with one OAuth client, the installations and the features of each device (one call each; radio devices are not read, at most 6 devices), anonymized with the troubleshooting rules, and makes a compact summary: one line per feature with its values and commands, at most 600 lines, written to the app's log between markers, so that a diagnostic report sent from the Homey app carries it. It works with only a login: `pair_check` offers it (`prepare_report`), and so does the settings page (`POST /report`). Nothing is sent by the app.

## Heating circuits

The config, capability IDs and Flow cards only know `heating.circuits.0.*`. Each device works on one heating circuit, `heatingCircuitId`: circuit 0 when it is enabled, otherwise the first enabled circuit, or the circuit chosen in the advanced device setting `heatingCircuit` (dropdown: `auto`, the default, or `0`–`3`; a circuit the installation does not have is refused with a translated message from `locales/*.json` → `device_settings`, and nothing changes). Users see circuits counted from 1, as in the ViCare app (`circuitNumber` in `heatingCircuit.js`): the setting's labels say circuit 1–4 and the refusal names them so; the setting's values, the store and the `data.id`s keep the API's index. `heatingCircuit.js` maps the API's `heating.circuits.<id>.*` features to `heating.circuits.0.*` when reading (and drops other circuits), and back to `<id>` for the poll filter and commands. A device on circuit 1 therefore has the same capability IDs as one on circuit 0, and readings, operating mode, heating target temperature, commands and the poll filter all use the same circuit. Devices paired before circuit support get their circuit from the one-time upgrade refresh, without re-pairing and without touching Flows. Changing the setting (`deviceSettings.js` → `changeHeatingCircuit`) reads all features once, merges the metadata (the feature list only grows), shows the new circuit's values from that same read (per-circuit capabilities the new circuit does not report get the value null and stay; `heating-mode-changed` does not fire for the switch itself) and pauses the device's poller meanwhile: its backoff and Retry-After are kept, and no extra poll is made.

Optional devices beside the ViCare device, each its own driver and entry in "Add device", so that adding the ViCare device stays as it is. They are for users who want a part of their Viessmann device as a device of its own: Google Home (Homey's cloud integration understands only class `thermostat` as a climate device), the Matter bridge (it reads only top-level standard capabilities and the modes heat, cool, auto and off), voice assistants, Homey's Climate view and zones. The ViCare device keeps everything it has; nothing about it changes.

- **Configuration** (`extraProfiles.js`, pure): which capabilities a device gets from its stored features (only ever added: a sensor reported for the first time adds its capability), their options, the paths a poll needs, the device's part of a response, its values and what a write sends. A capability's `paths` are also the paths its writes go to: the circuit's program picker has the active program and each program's own feature, all polled (in the same request, no extra call), since which of a program's commands can run (`isExecutable`) depends on the program running; every response refreshes the device's commands (`updatedCommands`), and a program reported for the first time is stored with its commands. Heating circuits and hot water read the datapoints of `config/` through `featureMapper.readValues`, on their own circuit (`heatingCircuit.js`); rooms are read in `extraProfiles.js`, since their paths are no datapoints of the ViCare device.
- **Shared poll** (`driver.js`): the ViCare driver keeps one poller per Viessmann device (`pollingKey`) with the Homey devices that show it: its own device (`main`) and the extra devices (`follow`/`unfollow`, the *followers*). A poll asks once for the main device's paths plus every follower's (`pollFilter(circuit, extraPaths)`) and hands the same response to each, so heating circuits and hot water cost no API calls. Without a main device, the first follower makes the request with only the followers' paths (never the extended poll), at the automatic interval or the followers' own (`pollInterval()`: rooms 15 minutes, `ROOM_POLL_INTERVAL`); such a Viessmann device counts as a polled device for the automatic interval (rooms do not) and in `plannedCallsPerDay`. A main device added later polls at once (`DevicePoller.pollNow`) and takes over; when it is deleted, the followers keep the poller. A follower that joins gets the last response; when that holds none of its values (another circuit, or no poll yet), the next poll comes 10 seconds later (`DevicePoller.pollSoon`, shared by followers joining together; a running poll, backoff and Retry-After are respected). Poll errors make every device of the key unavailable with the same message; a follower's own failure is logged and never fails the poll for the others. A follower ignores a response without any of its features.
- **Devices** (`extraDevice.js`; each driver's `device.js` only sets `KIND`): an extra device stores what pairing read of its part (`installationId`, `gatewaySerial`, `deviceId`, `roles`, `heatingCircuitId` or `roomId`, `features`, `constraints`, `commandMetadata`, the circuit's `operatingModes`, `version`), trimmed to the paths of its values (and of the circuit's programs). It writes through the configured capability it shows (`capabilityWrites.writeCapability`, so `commands.js`, the account's allowance in `writeQuota.js`, the command checks and the write check apply as on the ViCare device; its driver's `plannedCallsPerDay` asks the ViCare driver). A listener ignores a value that equals the current one (a Matter bridge or voice assistant repeating it). Only a poll error or data the device cannot use makes it unavailable; like the ViCare device it marks itself seen and available after a poll through `featureUpdates.js` (`markSeen`, `setAvailabilitySafely`), so Homey refusing either is only logged. The device checks its writes like the ViCare device (`ExtraDeviceMonitor`, a `DeviceMonitor` that only checks writes); faults, frozen values and computed values stay on the ViCare device. A value that changes fires its driver's trigger cards with a kind (`fireValueTriggers`, as on the ViCare device). Heating circuits have Flow cards of their own for their operating mode and program (see *Flow cards*); for everything else Homey's own thermostat and sensor cards cover the extra devices.
- **Pairing** (`extraDriver.js`, `extraPairing.js`): `intro` (the same view in every extra driver, copied from `drivers/heating-circuit/pair/intro.html`; the driver's `introTexts` say who needs the device and what it shares, from `locales/*.json` → `pair.extra`), `client_id` (a copy of the ViCare driver's view; `extraDevices.test.js` fails when a copy is not byte-identical to its source), `login_oauth2` (homey-oauth2app skips it when the app has a saved login, so the devices share the ViCare device's login), `list_devices`, `add_devices`. The device list reads the installations and the features of each Viessmann device of the right type once (heating devices for circuits and hot water, `roomControl` for rooms) and lists only what the account has: every enabled circuit with a set point or a mode, hot water with a set point, every room with a temperature sensor. Names: `<model> heating circuit <n>` (counted from 1 like the ViCare device's circuit setting, with the circuit's own name when it is more than a default name), `<model> hot water`, `Smart Climate room <n>` (numbered from 1; the API has no room names). A list with nothing to add says so per kind.

## Commands

Every write goes through `commands.js` → `sendFeatureCommand` (the place for anything that must happen around every write): capability writes (`device.executeCommand` → `sendCapabilityValue`, with `capabilityCommand` building the command and parameters from the capability's `command` config), the commands a derived capability plans (`sendCommands`), the holiday program, the heating curve and the generic command card. Capability listeners and Flow actions without a kind call `device.writeCapability(name, value)` (`capabilityWrites.js`): a configured capability writes on the path `commandTarget` picks for the device, a derived capability sends the commands its `write` plans, in order (the program picker ends comfort before it starts eco, for example), and the last one confirms its values. After its checks it takes the write from the account's allowance (see *API quota*), and after a successful write it hands the values to confirm to `deviceMonitor.js` (see *Device status*); a 403 gets the translated "Viessmann refused the change" text. It checks the command against `commandMetadata` (`lib/commandValidation.js`: exists, `isExecutable`, required parameters, type, enum, min/max/stepping) and, for the operating mode, against the circuit's modes (`set-operating-mode` offers `forcedNormal` and `forcedReduced` too; a mode the circuit does not have is refused with an error), before calling the API. A response with `data.success: false` is an error, and capability values are only updated after a successful command (also the other capabilities that show the same property, e.g. `target_temperature` with `target_temperature.heating`). The derived capabilities then follow at once (`showWrittenValues` in `capabilityWrites.js`): they are computed with `readCapabilityValues`, as the next poll will compute them, from the features the device last heard of (`featureCards.knownFeatures`) with the written property values in place (`withWrittenValues`), without an API call. So `thermostat_mode` shows the standard mode of a new operating mode right away, and ending the holiday program takes it out of the status text. Polls keep the metadata current; until a device has any (no refresh and no poll yet), the check is skipped.

The program picker switches comfort and eco on (switching one on first switches the other off); normal and reduced follow the device's time program, so choosing one only ends comfort or eco, and is refused otherwise. Modules without a device (`config/*.js`, `holiday.js`) throw an error whose `code` is a `flow.*` key; `userErrorFrom` (`userErrors.js`) turns it into the user's text.

## Flow cards

Defined by hand in each driver's `driver.flow.compose.json`, with their texts inline (the cards added in 2.0.0 in every app language): the ViCare driver's, and the heating circuit's (below). Homey adds the device argument with `driver_id=<driver>` to each, so a driver's cards are offered only on its own devices. Card ids are app-wide: `registry.test.js` checks that no id is used twice. `flowCards.js` maps each card id to the capability it works on. `driver.js` registers the trigger cards and keeps them per capability; `flowHandlers.js` → `registerFlowCards` registers the condition and action cards. Cards without a `kind` read or write their capability directly:

- Conditions `compressor-is-running`, `burner-is-running`: the current capability value.
- Actions `set-operating-mode`, `set-heating-thermostat`, `set-hot-water-thermostat`, `set-hot-water-thermostat2`, `do-one-time-hot-water-charge`, `set-fuelcell-mode`, `set-heating-program`, `set-heating-reduced-thermostat`, `set-heating-comfort-thermostat`, `set-hot-water-hysteresis`: the run listener writes the first argument with `device.writeCapability` (see *Commands*).
- Trigger `heating-mode-changed` (token `mode`), fired from `setCapabilityValueIfPossible` (`featureUpdates.js` → `showValue`) through `driver.getTriggerCard`.
- Event triggers (`event: true` in `flowCards.js`): `fault-reported`, `logbook-entry-added`, `event-logged`, `event-code-logged`, fired by `deviceMonitor.js` through `driver.triggerEvent` with their own tokens. Their `$filter` is `alarm_problem`, which every device has.

Cards with a `kind` run in `flowHandlers.js`, from one table per card group keyed by kind (`CONDITIONS`, `TRIGGERS`, `ACTIONS`, `AUTOCOMPLETE`); a new card type is a mapping in `flowCards.js` plus one entry there, and `flowHandlers.test.js` checks that every kind has its handler:

- **Conditions** `isOn` (`circulation-pump-is-running`, `hot-water-circulation-pump-is-running`, `heating-is-active`, `holiday-is-active`), `equals` (`operating-state-is`, `heating-program-is`: the value is the card's dropdown `argument`), `chooseValue` (`circuit-operating-mode-is`, `circuit-program-is`: the value is the entry chosen in the card's autocomplete `argument`), `compare` (`outside-temperature-is`, `supply-temperature-is`, `hot-water-temperature-is`, with a dropdown above/below and a number) and `compareFeature` (`feature-value-is`, see the generic cards). They fail with a translated message while the value is unknown (null) instead of answering "no".
- **Triggers** `turnedOn`/`turnedOff` (`circulation-pump-started`/`-stopped`, `hot-water-circulation-pump-started`/`-stopped`, `heating-started`/`-stopped`), `changed` (`outside-temperature-changed`, `supply-temperature-changed`, `hot-water-temperature-changed`, token `temperature`) and `valueChanged` (`operating-state-changed`, `heating-program-changed`, the new value as the mapping's `token`; a program the picker does not show is no value, so a switch to or from it fires nothing). `driver.getValueTriggers(capability)` lists them; `setCapabilityValueIfPossible` fires them only for a change from a known value, so the first value after pairing, after a start or after a gap (value cleared) fires nothing, and neither do updates without triggers (a heating circuit switch). The card ids do not follow Homey's `<capability>_changed` convention, so Homey never fires them on its own as well.
- **Chosen values and the holiday program**: `chooseValue` (`set-device-operating-mode`, `set-hot-water-mode`, `set-circuit-operating-mode`, `set-circuit-program`) writes the entry chosen in the card's autocomplete `argument`, which lists the values the capability has on the device in Homey's language; `startHoliday` (`start-holiday`: Homey's date argument `DD-MM-YYYY`, also `YYYY-MM-DD`, checked to be real dates with the end not before the start, and not on the same day where the command says `sameDayAllowed: false`) and `endHoliday` (`end-holiday`) in `holiday.js`.
- **Heating curve** (`heatingCurve.js`): `set-heating-curve-shift`, `adjust-heating-curve-shift`, `set-heating-curve-slope`. `setCurve` takes both values, so the other one is sent as the read-back capability (`measure_curve_number.circuit0Shift`/`.circuit0Slope`) shows it. The read-back capabilities are hidden from the device view (`uiComponent: null` in the capability definition) and kept for `$filter`, Flows and Insights. Values are rounded to the command's stepping, checked against its constraints, and a value the curve already has is not sent.
- **Temporary changes** (`boost.js`): `boost-hot-water` (hot water target for N minutes), `boost-heating-curve-shift` (shift ±N for N minutes), `boost-hot-water-charge` (one-time charge, stopped after N minutes if it still runs), `end-boosts`. See *Temporary changes*.
- **Generic cards** (`featureCards.js`), on every device (no `$filter`): `read-feature-number` and `read-feature-text` (Advanced Flow only, since they return a token), the condition `feature-value-is` (any numeric value above or below a number, also in standard Flows) and `run-feature-command`, with autocomplete. Reading uses the values of the last poll for polled features; any other feature is read from the API on its own and reused for 1.5 poll intervals. The autocomplete lists every feature from the last complete (unfiltered) response, the device's own extended poll or a read made for it, reused for an hour; a read that is running is shared (a complete one also with single reads), so a device never has two reads of the same features at a time; commands come from the device's command metadata (executable ones only). A command's parameters are JSON, checked against the command metadata (no unknown parameters) before sending.

Writes from these cards are limited per device, kind of write and hour (`writeLimits.js` → `WRITE_LIMITS`: 12 heating curve changes, 12 hot water boosts, 12 charges, 30 generic commands), to stop runaway Flows rather than normal use such as a Flow every 5 minutes. A new kind is one entry, counted with `takeWrite`; a further reason to refuse a Flow card's write is one more function in `WRITE_CHECKS`. The account's daily quota and burst limit apply to every write, also from the device view, so they are in `sendFeatureCommand` (see *API quota*). A value outside the device's limits is refused before it counts, an unchanged value is not sent, and restoring a temporary change is never limited. Every error a Flow card or a command shows the user comes from `userErrors.js` → `userError(device, key, tags)`: the text `flow.<key>` in `locales/*.json`, translated by `lib/errorMessages.js` with the English text as the fallback, and the key as the error's `code` (the operating mode a circuit does not have is one of them).

**Heating circuit cards** (`drivers/heating-circuit/driver.flow.compose.json`; `EXTRA_FLOW_CARDS.circuit` in `flowCards.js`): `set-circuit-operating-mode`, `set-circuit-program` (actions), `circuit-operating-mode-is`, `circuit-program-is` (conditions), `circuit-operating-mode-changed` (token `mode`), `circuit-program-changed` (token `program`). They work on the circuit's own `thermostat_mode.heating` and `thermostat_mode.heatingProgram` with the kinds above, and their autocomplete lists the circuit's own modes and programs. `extraDriver.js` registers them (`onOAuth2Init`: the run listeners through `registerFlowCards`, the triggers per capability through `valueTriggerCards`, which `driver.js` uses too); the ViCare device's cards stay its own. A new kind of extra device with cards gets an entry in `EXTRA_FLOW_CARDS` and a compose file in its driver folder.

Every card that works on a capability has `$filter: capabilities=<its capability>` (`end-boosts`: any of its three, `a|b|c`), so Homey offers it only on devices that have it. On a device without the capability a card could not work anyway: actions are refused by the command check or reach a feature the device does not have, the conditions read no value, and the trigger never fires. `flowCompose.test.js` checks every driver's compose file in place of the old generator: texts in English and only in app languages (cards with a kind: in every app language), formatted titles that use exactly the card's arguments, and each `$filter` matching the runtime mapping and a capability the driver's devices can have. The capability matrix lists the cards each fixture device gets.

### Temporary changes

`boost.js` keeps what has to be undone in the store key `boostRestores` (`{ hotWater: { previous, boosted, until }, curveShift: {…}, hotWaterCharge: { until } }`), written before the change is sent and reverted if sending fails. A timer (`homey.setTimeout`) restores it at `until`; on start, `onOAuth2Init` schedules the stored restores again (one that came due while Homey was off runs 2 minutes after the start, after the first poll). A restore only undoes the boost's own change: when the value differs from the boosted value, someone changed it in the meantime and it is left alone. A second boost of the same kind keeps the original previous value and extends the end time. The charge boost stops only the charge it started and has seen running since: the device reports every value change to the boosts (`valueChanged`), a charge seen ended finishes the charge boost, and a charge that already ran when the card ran, or one running after a restart (when that can no longer be told), is left to end by itself. A failed restore is retried every 5 minutes and given up (logged) a day after its time. Unloading or deleting the device stops the timers; the store keeps what is pending.

### Optional groups

`optionalGroups.js` lists groups of values that a device setting turns on (today `diagnostic`, the checkbox `diagnosticValues`, off by default, in the settings group "Optional values"). A feature with `group` gets its capabilities only while its group is on; `onSettings` adds or removes them right away (`applyEnabledGroups` in `deviceSettings.js`), without an API call. Turning a group off removes exactly its capabilities, with their Insights history, which the setting's hint says. Only new values go into a group; capabilities devices already have are never moved into one. The capability matrix lists per fixture what each group would add (`groups`).

Homey also generates threshold triggers for number capabilities (e.g. "Hot water temperature becomes greater than"); users rely on those, which is one more reason capability IDs never change.

## OAuth client (`lib/ViessmannOAuth2Client.js`)

- `CLIENT_ID` comes from `homey.settings.get('clientId')`; pairing fails with `pair.no_client_id` when it is missing.
- PKCE: every login (pairing or Repair) gets a new code verifier (`onHandleAuthorizationURL`); its S256 `code_challenge` goes on the authorization URL, and the verifier on the token request of that login, once (`onGetTokenByCode`; a second exchange needs a new login). Refreshing the token of an existing session needs no verifier.
- HTTP: API and token requests use Node 22's global fetch through `lib/http.js` instead of homey-oauth2app's node-fetch 2, whose handling of keep-alive connections reported "Premature close" for complete responses. The client overrides homey-oauth2app's `_executeRequest` only to swap fetch (and to await a token refresh in progress before it builds a request). A failure without a response is a `FetchError` with node-fetch's `type` (`request-timeout`, `body-timeout`, `system`, `invalid-json`) and no URL in its message.
- `onHandleNotOK` returns errors from `lib/apiError.js` (`onIsRateLimited` lets a 429 through to it, so its body is read): `Viessmann HTTP <status>: <description> — <details>`, where the details are Viessmann's `errorType`/`message` or the IdP's `error`/`error_description`. From `extendedPayload`, which can contain IDs, only a short reason code (`reason`, e.g. `GATEWAY_OFFLINE`) and a 429's `limitReset` are read; tokens are redacted. Errors carry `status`, `apiCode`, `apiReason`, `requestId` and, for 429, `retryAfterMs` (the later of `Retry-After` and `limitReset`). `apiErrorState()` classifies the error states above. A 401 that is still there after the SDK refreshed the token keeps its status.
- `onRefreshToken` only replaces the stored token when the response contains a valid access token; a missing refresh token in the response keeps the old one. Failed token requests become `tokenError`s that keep the IdP's `error`/`error_description` and set `authenticationFailed` only for 401, `invalid_grant` and `invalid_client`. `debug` output (homey-oauth2app logs every request when debugging) has tokens and the code verifier redacted and ids masked.
- The log never shows the Client ID, installation ids or gateway serials in full: `lib/logPrivacy.js` keeps their last three characters (`…001`), also in the device key the driver logs (`…678-…001-0`). Responses are never logged in full; the device's debug line logs counts.
- `getFeatures` always adds `skipDisabled=true`; with a filter it requests only the given paths.
- `getInstallations` returns the response as the API sends it, with the real ids that pairing needs. Pairing logs only a summary of it (counts, device types and models).

## Settings page and Web API

`settings/index.html` saves the Client ID, says who needs the optional extra devices and what they cost in API calls, shows the status (`GET /health`: per Viessmann login the API calls used today and planned per day; per device its interval, last successful update and last error, kept in memory by `deviceMonitor.js`, error messages masked like in the log; the devices are the ViCare devices and the extra devices that make calls of their own, `driver.sharedPollDevices()`: rooms, and heating circuits or hot water without a ViCare device), and offers the report for the developer (`POST /report`, see *Report for the developer*) as its troubleshooting tool, through `api.js`. The Web API is for the settings page only.

Users share the report, so it is anonymized with `lib/anonymize.js` (`TROUBLESHOOTING_STYLE`): serials, installation, gateway and device ids (also inside `uri`), material numbers and zigbee ids become placeholders such as `anonymized-installation-1` and `anonymized-serial-1`; the address, descriptions, building contact fields, the service partner and user-defined circuit names become `anonymized`. Generic device ids (`0`, `gateway`, `TCU`, `HEMS`, `RoomControl-1`), feature names, values, units, timestamps, commands and constraints are kept. One `Anonymizer` per app instance numbers the placeholders in order of first appearance, so the same real value gets the same placeholder in the installations and every device's features, and in later reports, until the app restarts. The test fixtures use the same rules with `FIXTURE_STYLE` (realistic fake values, normalized timestamps).

## Versions and migrations

`device.js` → `checkUpgradeSpecifics` runs `migrations.js`: a registry with one step per release that changed the store (1.0.4: ids, roles and operating modes move from the device data to the store; 1.0.9: the store records its version; 1.0.15: heating circuit and command metadata are read once; 2.0.0: `dailyCounters` and `knownMessages` start empty). The optional store key `boostRestores` (2.0.0, see *Temporary changes*) needs no step: a device without it has nothing to restore. Every step decides from the store whether it is needed, so steps are idempotent and run oldest first on every start; a step that fails, or whose own error handling skips it (the metadata read), runs again on the next start. Store keys are frozen: a step adds or fills in keys and never renames or removes one. When the store schema changes, append a step with the version that introduces it and add its upgrade test to `migrations.test.js`. A release bumps `version` in `.homeycompose/app.json` and adds an entry to `.homeychangelog.json`. `versionBefore` (and `storeVersionBefore`) compares three-part versions only.

## Recipes

**Add a datapoint**

1. The theme module in `config/` that fits (or a new one, added to `MODULES` in `config/index.js`): add a `PATHS` constant and a `FEATURES` entry, reusing the factories in `templates.js`. Use a non-deprecated feature path. A new capability lands in the group of its prefix in `order.js` → `CAPABILITIES` (or at the end); add an entry there only to place it on purpose. A value combined from several features is a `DERIVED` capability instead.
2. A new base capability (not a Homey system capability) needs `.homeycompose/capabilities/<base>.json`. Sub-capabilities (`measure_temperature.<x>`) don't.
3. Add the new capability ID to `drivers/vicare/__tests__/registry.json` and update `config.test.js`.
4. If a fixture contains the feature, `device.test.js` covers it automatically; otherwise add an anonymized fixture.
5. `npm run matrix` and check the diff of the capability matrix: the new capability shows up on exactly the fixture devices that report the feature.
6. `npm run test:coverage`, `npm run lint`, `npm run typecheck`, `npm run homey:validate`.

**Add a Flow card**

1. Add it to the driver's `driver.flow.compose.json` by hand (`drivers/vicare/`, or an extra device's driver folder), with its texts inline in every app language you can provide (at least English) and `"$filter": "capabilities=<capability>"`. The id must be new across the app.
2. Map its id to the capability in `flowCards.js` (an extra device's cards in `EXTRA_FLOW_CARDS`). Actions without a `kind` need a `capability` that exists in `FEATURES` or `DERIVED`; anything else is a `kind` in `flowHandlers.js` (an existing one, or a new entry in its table). A kind that several cards share reads the card's argument from `argument` (`equals`, `chooseValue`) or names its token in `token` (`valueChanged`); event triggers have `event: true`.
3. Register the card in `registry.json`, run `npm run matrix`, then the checks above.

**Add an optional group**

1. Add the group to `GROUPS` in `optionalGroups.js` and a checkbox setting with the same id (in the settings group "Optional values" of `driver.compose.json`, its hint saying that turning it off removes the values and their history), registered in `registry.json`.
2. Give the new features `group: '<name>'`. Never a capability that devices already have.
3. `npm run matrix`: the fixture devices list the group's capabilities under `groups`.

**Change a capability's options or texts**

1. Change its `capabilityOptions` in its module in `config/`. `updateCapabilityOptions()` reapplies them on every start, so devices that already have the capability get the change without re-pairing. To change an option, set its new value; don't leave it out, or a device may keep the old one.
2. Texts users see (`titleTrue`/`titleFalse`, `insightsTitleTrue`/`insightsTitleFalse` on the timeline and in Insights, translated `units`) go into every app language: English, German, Dutch, French and Swedish. The running states (`measure_*_active`) carry the same texts in `.homeycompose/capabilities/`; `config.test.js` checks that they match.
3. Once a capability logs Insights (`preventInsights: false`), keep it that way: users build on that history. The statistics counters log Insights since 1.0.15; they have no Flow tag (`preventTag: true`), since a tag once offered cannot be taken back without breaking Flows.
4. Update the golden copy in `config.test.js` and run `npm run matrix`, then `npm run test:coverage`, `npm run lint`, `npm run homey:validate`.
